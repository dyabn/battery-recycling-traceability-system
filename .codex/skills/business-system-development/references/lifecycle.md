# 生命周期流程

本 Skill 采用“业务先行、确认推进、切片实现、持续回写”的项目生命周期。任何阶段产生的新问题都应进入开放问题清单，不能用猜测代替确认。

## L0 项目材料整理

目标：收集并索引课程模板、课堂要求、业务资料、用户确认记录和已有项目文件。

输出：

- 材料来源清单
- 可引用资料列表
- 初始开放问题清单

不得在本阶段生成系统功能、数据库或代码。

## L1 业务定位

目标：说明业务为什么存在、服务谁、解决什么问题、暂不解决什么问题。

输出：

- 《业务定位说明 V0.1》
- C1 业务定位确认记录草案

动力电池项目第一次运行本 Skill 时，应生成《动力电池回收流转与追溯业务定位说明 V0.1》。

## C1 业务定位确认

C1 确认后，才能进入全局业务基线建立。确认前只能修改业务定位，不得开始系统设计。

## L2 建立全局业务基线

目标：建立业务全景，不追求所有细节一次到位。

至少覆盖：

- 业务名称
- 业务背景和痛点
- 业务目标
- 范围和边界
- 参与者和角色
- 核心业务对象
- B0 总业务场景
- 业务结构分解
- 关键业务节点的 Who / What / Value
- 主要业务规则候选
- 主要异常候选

输出：

- 全局业务基线 V0.x
- 业务结构模型源文件
- 开放问题清单

## C2 全局业务基线确认

C2 确认后，才能选择并正式展开首个垂直业务切片。

## L3 选择首个垂直业务切片

目标：选择一个低外部依赖、高演示价值、状态变化清晰、能闭环测试的业务切片。

候选切片应使用评分表比较：

- 业务价值
- 外部依赖
- 数据对象清晰度
- 人到人闭环程度
- 状态变化清晰度
- 异常覆盖价值
- 测试可验证性

动力电池项目可暂定候选切片：回收接收 -> 验收 -> 入库 -> 形成库存记录。最终仍需在 C2 后确认。

## L4 业务切片详细分析

目标：把已确认切片拆成可验证业务过程。

至少覆盖：

- 流程步骤
- 角色分工
- 输入输出
- 状态机
- 业务规则
- 异常路径
- 人工判断与系统承担边界
- 信息流和数据流

输出：

- 切片业务流程说明
- BPMN / UML 活动图源文件
- 状态机说明
- 规则清单
- 异常清单
- 人机边界表

## C3 业务切片确认

C3 确认后，才能推导正式系统需求。确认前不得把业务动作直接变成页面或接口。

## L5 系统需求推导

目标：从已确认业务切片推导系统能力。

至少形成：

- 用户需求
- 功能需求
- 非功能需求
- 用例
- 权限需求
- 数据需求
- 接口候选

所有需求都必须能追溯到业务节点、业务规则或异常场景。

## L6 验收标准和测试用例

目标：先定义如何验收，再进入原型和编码。

输出：

- 验收标准
- 正常路径测试用例
- 异常路径测试用例
- 权限测试用例
- 数据一致性测试用例

验收标准未建立时，不得开始编码。

## L7 UI、API、Mock 原型验证

目标：通过低成本原型验证系统交互、接口契约和业务闭环。

输出：

- UI 原型
- API Mock 契约
- 原型验证记录
- 问题和变更记录

## C4 原型确认

C4 确认后，才能冻结数据库、接口和代码结构。未确认前只允许原型级调整。

## L8 数据库、接口和部署设计

目标：把已确认需求转化为工程设计。

输出：

- 数据库设计
- 接口契约
- 部署设计
- 权限设计
- 日志和追溯设计

## L9 系统架构与代码结构设计

目标：建立前端、后端、数据库、测试和文档的工程结构。

输出：

- 架构说明
- 代码结构说明
- 模块边界
- 自动化测试计划

## L10 编码与自动化测试

目标：只实现已确认、可验收、可追踪的需求。

输出：

- 代码
- 数据库迁移脚本
- 单元测试
- 集成测试
- 端到端测试
- 测试报告

## L11 回写需求和业务基线

目标：将实现过程中的有效变更回写到业务基线、需求、测试和追踪记录。

输出：

- 更新后的业务基线
- 更新后的需求追踪表
- 变更影响分析
- 下一切片建议

## L12 开发下一个业务切片

重复 L3 到 L11。每个切片都必须独立确认、独立验收、独立回写。
