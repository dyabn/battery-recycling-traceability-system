# 阶段门禁

阶段门禁用于控制项目推进节奏。门禁不是形式确认；它决定下一类工作是否允许开始。

## C1 业务定位确认

确认对象：

- 业务名称
- 服务对象
- 价值承担方
- 业务痛点
- 业务目标
- 范围和边界
- 参与者
- 核心业务对象
- 系统在现实业务中的作用
- 暂不实现内容
- 开放问题

通过条件：

- 用户明确确认业务定位可作为 V0.1 基线。
- 未确认问题已经进入开放问题清单。

未通过时：

- 只能继续修改业务定位。
- 不得建立冻结的全局业务基线。

## C2 全局业务基线确认

确认对象：

- B0 总业务场景
- 业务结构分解
- 核心业务对象
- 业务角色和职责
- 主要业务规则候选
- 主要异常候选
- 首个业务切片选择依据

通过条件：

- 用户确认全局业务基线可作为当前分析依据。
- 首个切片已通过评分或明确选择。

未通过时：

- 不得展开正式业务切片。
- 不得推导系统需求、页面、接口或数据库。

## C3 业务切片确认

确认对象：

- 切片业务流程
- 角色分工
- 状态流转
- 业务规则
- 异常路径
- 人机边界
- 信息流和数据流

通过条件：

- 用户确认切片业务逻辑可作为需求推导依据。
- 关键规则都有来源或被用户确认。

未通过时：

- 不得生成正式需求规格。
- 不得将业务动作直接设计成页面或接口。

## C4 原型确认

确认对象：

- UI 原型
- API / Mock 契约
- 验收场景
- 权限边界
- 数据输入输出
- 异常提示和处理方式

通过条件：

- 用户确认原型可以指导工程实现。
- 验收标准和测试用例已经建立。

未通过时：

- 不得冻结数据库。
- 不得冻结接口。
- 不得生成正式前后端代码结构。

## 全局停止条件

出现以下情况时必须停止推进，并向用户说明需要确认的内容：

- 业务不清楚时，不生成系统功能。
- 业务规则没有依据时，不允许 AI 猜测。
- C1、C2、C3 未确认时，不进入正式系统设计。
- 验收标准和测试场景未建立时，不开始编码。
- 原型没有完成 C4 验证时，不冻结数据库和接口。
- 任何变更必须记录影响范围并更新基线。
- 不允许一次性生成整个系统。

## 变更处理

任何影响已确认内容的变更都应记录：

- 变更编号
- 变更来源
- 影响的业务节点
- 影响的规则、需求、测试、原型、接口、数据库或代码
- 是否需要重新确认 C1、C2、C3 或 C4
